## 写在前面

这篇是上一篇 [政务系统可观测平台搭建实战：SigNoz + OpenTelemetry 探针](/posts/signoz-opentelemetry-observability-guide/) 的续集。

上一篇写的是"把平台和探针装起来"——SigNoz、ClickHouse、OTel Collector，给 5 台服务器 9 个应用挂探针。那一篇写完的时候，平台能跑、图表能出，我以为活儿干完了。

事实证明只干了一半。

**平台"能跑"，和平台"能说清数据、能看借口"，完全是两件事。** 这次的任务是把一套已经装好的可观测平台，从"装完什么样就是什么样"变成"乌兰察布这套系统该有的样子"。中间动的东西比我想的多：

- 前端页面里全是历史环境的地址——IP、仪表板 UUID、工单接口、SDK 上报地址，一个都不能直接用
- CMDB 里 1000 多条全是示例数据，主机名叫 `SRV-202401001`，接口路径里带 `guizhou`，一眼就知道不是我们这套
- 给应用挂探针，重启一个系统直接起不来，日志只有一行提示，什么都没说
- 接口监控页面录了 138 个接口，调用次数全是 0
- 最后查出来的原因是：**可观测平台那台服务器的系统时钟慢了 29 分钟**

这些坑有个共同点：**报错信息不会告诉你在哪。** 只能一层一层往下挖。

排查过程中我大量用了 AI 帮忙：反编译 class 文件看逻辑、写批量查 ClickHouse 的脚本、比对两份配置的差异、生成验证命令。说句实话，没有 AI 我大概要多花三四倍时间，特别是反编译和写查询脚本这两块，它比我手快得多。

但 AI 也有明显的短板：**它不知道现场。** 有一次它判断某个应用起不来是"外网授权服务不可达"，让我去查网络。我回了一句"网络一点没动，就是重启了一下"，它才转向去查 jar 包，最后在反编译出来的字节码里找到了一个硬编码的日期。类似的情况还有几次，所以每个结论我都得自己再验一遍。

这篇会写：

1. **20 个问题**的现象、怎么查出来的、最后怎么解决的
2. 改了哪些文件、**每处改动到底是干什么的**
3. 踩过的坑，以及下次怎么少踩

### 1.2 问题详述

#### 问题 1：网关全部接口返回「缺少Authorization」

**现象**

```
GET /gate/bspplus/user/login  →  {"code":0,"msg":"缺少Authorization","status":400}
```

所有经过网关的请求都被拦下，包括本该免登录的登录接口。

**根因**

网关的鉴权链路由两个过滤器组成：

- `GlobalApiAuthFilter`：负责 `anon-white-list`（匿名白名单）和 `session.loginuris`
- `GlobalAuthorizationFilter`：负责 `tokenWhiteList`（Token 白名单）

网关配置里 `api-auth-check-enable: false` **关闭了 `GlobalApiAuthFilter`**，导致 `anon-white-list` 里的配置**完全不生效**。最终只有 `GlobalAuthorizationFilter` 在跑，而它只认 `tokenWhiteList`。

判断逻辑（反编译确认）：

```java
private boolean isWhite(String path) {
    return securityCustomConfig.getTokenWhiteList().stream()
            .anyMatch(p -> pathMatcher.match(p, path));
}
```

**处理**

在 Nacos 的 `dgov-cloud-gateway` 配置里，往 `tokenWhiteList` 追加 6 条：

```yaml
tokenWhiteList:
  - /gate/bspplus/utils/**
  - /gate/bspplus/user/login
  - /gate/bspplus/user/signOn/login
  - /gate/bspplus/oauth/**
  - /gate/bspplus/sso/**
  - /gate/bspplus/user/logout
```

**验证**

```
GET /gate/bspplus/utils/uuid  →  HTTP 200，返回 uuid
```

**教训**

网关有**两套**白名单机制，只改其中一套没用。排查时应当先确认哪个过滤器在生效（看 `api-auth-check-enable` 开关），再决定改哪个配置项。

#### 问题 2：服务启动即退出（license.dat 缺失）

**现象**

```
java.io.FileNotFoundException: class path resource [license.dat] cannot be opened
```

BSPPLUS 和网关日志打印 `Started` 之后立刻退出。

**根因**

`SystemApp.checkLicence()` 在启动时校验 License：

```
goto("utf-8") → ClassPathResource / FileUrlResource("license.dat")
→ Base64 + DES 解密 → 校验 JSON 里 code == "1"
```

`license.dat` 文件名在 `com.inspur.dgov.core.a.c.class()` 中硬编码（`ldc #20 'license.dat'`）。

**处理**

从已经正常运行的通用审批（XZSP）目录复用 `license.dat`：

```
D:\server\apache-tomcat-9.0.87-XZSP\...\license.dat
  → D:\server\inspur-digital-bspplus\license.dat
  → D:\server\dgov-cloud-gateway\license.dat
```

该 License 有效期至 **2031-03-03**。

**教训**

同一产品线的 License 通常可以复用。建议把可用的 `license.dat` 统一留存一份到 `D:\server\_license\`，后续服务重装直接拷贝。

#### 问题 3：`.dbmd` 建库脚本报排序规则不支持

**现象**

导入 `.dbmd` 时提示 `Unknown collation: 'utf8mb4_0900_ai_ci'`。

**根因**

`utf8mb4_0900_ai_ci` 是 **MySQL 8.0** 引入的排序规则，本环境是 **MySQL 5.7.17**，不支持。

**处理**

替换脚本内所有 `utf8mb4_0900_ai_ci` → `utf8mb4_general_ci`，重建后 147 张表创建成功。

#### 问题 4：数据迁移的三个问题

**4.1 字段超长**

```
ERROR 1406: Data too long for column 'USER_CODE'
```

表定义 `VARCHAR(36)`，源库实际数据 56 字符。

解决：`ALTER TABLE PUB_USER_ROLE MODIFY USER_CODE VARCHAR(100);`

**4.2 权限不足**

```
ERROR 1044 (42000): Access denied for user 'dgov_bsp'@'%' to database 'dgov_bsp_tmp'
```

解决：用 root 执行 `GRANT ALL PRIVILEGES ON dgov_bsp_tmp.* TO 'dgov_bsp'@'%';`

**4.3 数据传输工具无法跳过建表**

目标库已有表结构，工具仍强制建表导致冲突。

解决：建临时库 `dgov_bsp_tmp` 先导入，再用 SQL 从临时库搬到正式库：

```sql
INSERT IGNORE INTO dgov_bsp.PUB_ROLE SELECT * FROM dgov_bsp_tmp.PUB_ROLE;
```

**迁移结果**

| 表 | 源库行数 | 目标库行数 |
|---|---|---|
| PUB_ROLE | 75 | 71 |
| PUB_RESOURCE | 2708 | 2541 |
| PUB_ROLE_RESOURCE | 4318 | 1511 |
| PUB_USER_ROLE | 125814 | 125814（INSERT IGNORE） |

#### 问题 5：bat 脚本乱码、吞换行

**现象**

执行 `startup.bat` 时输出：

```
'+' 不是内部或外部命令，也不是可运行的程序
'笈低?' 不是内部或外部命令
'MX' 不是内部或外部命令
'上报地址:' 不是内部或外部命令
```

**根因（两个叠加）**

1. 文件用 `LF` 换行写出，而 `cmd.exe` 要求 `CRLF`
2. 文件内含 **GBK 中文注释**（`rem 应用: xxx`），cmd 逐行解析时把 `rem` 和中文拆开，中文碎片被当作命令执行

**处理**

`.bat` 文件统一规范：

```powershell
$lines = @('@echo off', 'set "JAVA_OPTS=..."', ...)
$text  = ($lines -join "`r`n") + "`r`n"          # 强制 CRLF
[System.IO.File]::WriteAllText($f, $text, (New-Object System.Text.ASCIIEncoding))  # 纯 ASCII
```

**规范（后续所有 bat 都遵守）**

- 换行**必须** `CRLF`
- 内容**必须**纯 ASCII，注释也用英文
- 不使用 heredoc 直接写文件（容易带入 LF）

#### 问题 6：执行 `startup.bat` 后命令行永久挂住

**现象**

```powershell
& cmd /c "startup.bat" 2>&1 | Out-String | Write-Host    # ← 卡死，不再返回
```

**根因**

`startup.bat` 内部调用 `catalina.bat start`，会 `start` 一个新窗口运行 java。**Java 进程继承了父进程的 stdout 管道句柄**，只要 java 活着，管道就不关闭，PowerShell 就一直等待。

**处理**

改用 `Start-Process`，**不接管输出**：

```powershell
Start-Process -FilePath "cmd.exe" `
    -ArgumentList "/c","startup.bat" `
    -WorkingDirectory "$base\bin" `
    -WindowStyle Hidden
```

**教训**

凡是**会驻留后台**的进程（Tomcat、java、nginx），都不要用管道接收它的输出，否则管道永不关闭。

#### 问题 8：网办后台（iWebSite）启动 10 秒后自动退出

**现象**

Tomcat 正常启动，Spring 容器初始化完成，然后**静默退出**，无异常栈：

```
14:41:12  Root WebApplicationContext: initialization completed in 9651 ms
14:41:12  com.inspur.app.utils.DateUtils.compareDate(DateUtils.java:43)
          - Application is not initialize...
          ↓ 等 10 秒
14:41:22  Closing Root WebApplicationContext
14:41:22  {dataSource-2} closed / {dataSource-1} closed
```

**排查过程**

1. 首先怀疑外网授权服务 `EXT-HOST-4:8081` 不可达 → **测了一下确实不通。但我回了一句"网络一点没动，就是重启了一下"，才意识到方向找错了**
2. 用 `javap` 反编译 `jcore-1.0.jar` 里的 `com.inspur.app.utils.DateUtils`

**反编译结果**

```java
private static final String expireDate = "2025-10-01 00:00:00";   // ← 到期日硬编码
public  static final String RUN_MODE    = "release";              // ← 本方法未使用，无旁路

public static JSONObject compareDate() {
    c1.setTime(df.parse("2025-10-01 00:00:00"));   // 到期日
    c2.setTime(new Date());                        // 当前时间
    int r = c1.compareTo(c2);

    if (r == 0)      { code="1"; log("Application is initialize..."); }
    else if (r < 0)  {                              // ★ 已过期
        code = "0";
        log("Application is not initialize...");
        Thread.sleep(10000);
        System.exit(0);                             // ★★★ 主动结束 JVM
    }
    else             { code="1"; log("Application is initialize..."); }
}
```

**根因**

`jcore-1.0.jar` 把到期日写死成 `2025-10-01`，当前日期（2026-10-27）超过后 `System.exit(0)`。

**为什么之前能跑**：旧进程是在 2025-10-01 **之前**启动的，运行时不重查。本次为接探针重启，才触发检查。

**对比扫描：其他产品都是新版 jar**

| Tomcat | webapp | jar | 到期日 | 状态 |
|---|---|---|---|---|
| ACCEPT | `Inspur.Dzzw.CloudAccept` | `jcore-3.5.jar` | `2118-10-01` | 正常 |
| Parallel | `Inspur.Dzzw.WebParallel` | `jcore-3.5.jar` | `2118-10-01` | 正常 |
| XZSP | `Inspur.Dzzw.WebApproval` | `jcore-3.5.jar` | `2118-10-01` | 正常 |
| **WebSite** | **`iWebSite`** | **`jcore-1.0.jar`** | **`2025-10-01`** | **已过期** |

**处理**

用公司已发布的 `jcore-3.5.jar` 替换：

```powershell
Copy-Item "...\XZSP\...\lib\jcore-3.5.jar"  $lib\jcore-3.5.jar
Move-Item  $lib\jcore-1.0.jar  $lib\jcore-1.0.jar.disabled-<时间戳>
```

**结果**

```
8030 LISTENING  PID 10252   ← 网办后台恢复
9996 LISTENING  PID 10252   ← JMX 探针同时生效
```

**教训（重要）**

1. `jcore-1.x` → `jcore-3.5` 跨大版本替换**兼容**（API 无破坏性变更），已验证
2. **每个老应用重启前都要确认 jar 版本与到期日**，否则一重启就炸
3. 我把这个结论反馈给了公司，让他们排查其他服务器上是否有同样的漏升级

#### 问题 9：换最新 license.dat 仍无法启动

**现象**

更换最新的 `license.dat` 后，重启仍然 10 秒退出。

**我的判断**

`DateUtils.compareDate()` **根本不读 `license.dat`**：

- `expireDate` 是 `static final` **编译期常量**，已内联进字节码
- 方法内唯一用到 License 的地方是 `com.iop.util.License.getLicenseName()`，**只取一个名字打日志**

所以换 license.dat 对这个问题**完全无效**。

**记录这一点的意义**：后续再遇到"启动即退出"且日志有 `DateUtils.compareDate`，直接查 jar 版本，不要再从 license 或网络方向排查。

#### 问题 10：告警「查看工单」点击后长时间无响应

**现象**

点击告警的「查看工单」：
- 先等约 30 秒
- 浏览器 DevTools 报 `Failed to load response data`
- 页面无任何提示

**根因**

前端 `dmsApi.js` 直连公司外网工单系统：

```javascript
DMS_API_ROOT: "https://dms.example.com"
DMS_ORDER_INFO_PATH: "/local/dsm-plugin-oms/api/order/getInfo"
DMS_HTTP_TIMEOUT: 30000          // 30 秒
```

`dms.example.com` 在本环境**不可达** → 请求挂 30 秒后才超时。

**关键：前端逻辑分支**

```javascript
const o = await post(DMS_API_ROOT + DMS_ORDER_INFO_PATH, { busiId });
if (o.state !== 1) {
    if (o.message.includes("TkOrder not found")) {
        err.code = "TK_ORDER_NOT_FOUND";   // → 前端弹「尚未生成工单，是否创建？」
    }
    reject(...);
}
```

**解决（不改前端代码，用 Nginx 造响应）**

在 `nginx.conf` 加两条 location：

```nginx
# ① 模拟「未找到工单」，让前端走友好分支
```

#### 问题 13：接口监控「调用总次数」始终为 0

**现象**

138 行接口全部显示 `调用总次数 = 0`、`接口状态 = 无流量`。

**根因**

前端 `signozService` 里的 SQL 用 `http.target` 做**精确匹配**：

```sql
AND attributes_string['http.target'] IN $http.route
GROUP BY attributes_string['http.route'] AS `接口地址`
```

而实际数据：

| 项 | 值 |
|---|---|
| 前端传的 `api_path` | `/Inspur.Dzzw.WebApproval/approval/workextend` |
| ClickHouse `http.target` | `/Inspur.Dzzw.WebApproval/approval/workextend?method=queryCount` ← **带查询参数** |
| ClickHouse `http.route` | `/Inspur.Dzzw.WebApproval/approval/workextend` ← **不带参数** |

`IN` 是精确匹配，`http.target` 带 `?method=queryCount` → 匹配失败。

**验证（直连 ClickHouse）**

```sql
-- 用 http.target 精确匹配
SELECT ... WHERE attributes_string['http.target'] IN ('/Inspur.Dzzw.WebApproval/approval/workextend')
-- → 0 条

-- 用 http.route 精确匹配
SELECT ... WHERE attributes_string['http.route'] IN ('/Inspur.Dzzw.WebApproval/approval/workextend')
-- → 764 条
```

**解决（前端补丁）**

`signozService-Cg3RwBMu.js`：

```sql
-- 改前
AND attributes_string['http.target'] IN $http.route
-- 改后
AND attributes_string['http.route'] IN $http.route
```

**第二层：网关 SQL 注入过滤器拦截**

改为 `http.route` 后，接口返回：

```json
{"code":0,"msg":"非法参数","status":400}
```

响应使用 `msg` 字段（网关格式），业务服务使用 `message` 字段，据此定位到网关。查网关配置：

```yaml
security:
  sql-injection-regex: ...|UNION.+?SELECT.+?FROM|INSERT\s+INTO.+?VALUES|(SELECT|DELETE).+?FROM|...
```

查询体里含 `SELECT ... FROM signoz_traces...`，命中 `(SELECT|DELETE).+?FROM`。

网关 Nacos 配置追加参数白名单：

```yaml
param-white-list[1]: /gate/obs/business/signoz/proxy/**
```

重启网关后，请求通过参数校验，卡在鉴权层（返回「缺少Authorization」），说明 SQL 过滤器已放行。

**第三层：SigNoz 服务器时钟偏差**

放行后数字能出来，但调 60 次只显示 3 次。经逐查询对比，定位为 SigNoz 服务器系统时钟慢 29 分钟，导致 `BETWEEN ... AND now()` 的时间窗上界偏移。详见「问题 19」。

**最终处理**

| 层 | 处理 |
|---|---|
| 第一层 | `signozService-Cg3RwBMu.js` 中 `http.target` 改为 `http.route` |
| 第二层 | 网关 Nacos 配置追加 `param-white-list[1]`，重启网关 |
| 第三层 | SigNoz 服务器执行 `hwclock --hctosys` |

**验证**

校时后，同一接口 `timestamp > now()-30m` 与 `BETWEEN now()-30m AND now()` 结果一致（14 = 14）；Postman 调 10 次后刷新页面，调用总次数随之增长。

#### 问题 19：SigNoz 服务器时钟偏差 29 分钟

**现象**

接口监控「最近 30 分钟」的数字不随新调用变化：调 60 次仍只显示 3 次。链路监控、指标监控、日志监控选择「最近 5 分钟」同样查不到最新数据。

**根因**

SigNoz 服务器 `SIG-HOST` 的系统时钟比实际慢 29 分钟，硬件时钟（RTC）正常：

```
Local time:     Tue 2026-10-27 17:08:43 CST      ← 系统时钟，慢 29 分钟
Universal time: Tue 2026-10-27 09:08:43 UTC
RTC time:       Tue 2026-10-27 09:37:37          ← 硬件时钟，正确
NTP enabled:    no
NTP synchronized: no
```

页面 SQL 为 `WHERE timestamp BETWEEN (now()-30m) AND now()`，其中 `now()` 取自 SigNoz 系统时钟。时间窗上界因此落在实际时间 29 分钟之前，窗口内只剩 29~59 分钟前的历史数据。

**验证方法**

同一接口两种写法对比，结果相差 3 倍：

| 写法 | 结果 |
|---|---|
| `timestamp > now() - 30m`（不设上界） | 15 条 |
| `timestamp BETWEEN now()-30m AND now()`（页面写法） | 5 条 |

三方时间对比（UTC）：

| 来源 | 时间 | 说明 |
|---|---|---|
| 应用服务器（写入 span） | 09:37:29 | 正常 |
| 运维终端 | 09:37:19 | 正常 |
| SigNoz 服务器 | 09:08:22 | 慢 29 分钟 |

**处理**

```bash
# 1) 确认硬件时钟正常
timedatectl status

# 2) 从硬件时钟同步系统时钟（该服务器无外网，无需安装 NTP 软件）
hwclock --hctosys

# 3) 确认
date
```

**验证**

```
ClickHouse now() : 09:40:29
终端 UTC          : 09:40:32
偏差              : 0.1 分钟
```

两种查法结果一致（14 = 14），最近 5 分钟数据实时可见，页面刷新后调用总次数正常增长。

**影响范围**

该偏差使所有基于时间窗的功能整体偏移：

| 功能 | 表现 |
|---|---|
| 接口监控调用总次数 | 显示 29~59 分钟前的数据 |
| 接口调用总览图表 | 时间轴与实际不符 |
| 链路 / 指标 / 日志监控「最近 N 分钟」 | 查不到最新数据 |
| 告警计算窗口 | 告警延迟约 29 分钟 |
| 按天分区边界 | 边界错位 |

**预防**

该服务器未启用 NTP（`NTP enabled: no`），时钟会持续漂移，29 分钟量级说明已漂移数周。建议：

1. 配置内网 NTP 源，启用 chrony 自动同步：
   ```bash
   yum install -y chrony
   vi /etc/chrony.conf      # server <内网NTP地址> iburst
   systemctl enable --now chronyd
   chronyc makestep
   ```
2. 若暂无 NTP 源，用计划任务定期从 RTC 对齐：
   ```
   0 3 * * * /sbin/hwclock --hctosys
   ```
3. 将「服务器时钟偏差」列入日常巡检项，与 ClickHouse 写入量一并检查。

### 2.4 `nginx.conf`

#### 完整结构

```nginx
worker_processes  1;
error_log  logs/error.log  warn;
pid        logs/nginx.pid;

events {
    worker_connections  1024;
}

http {
    include       mime.types;
    default_type  application/octet-stream;
    sendfile        on;
    keepalive_timeout  65;
    client_max_body_size 100m;

    server {
        listen       80;
        server_name  _;

        # ① 前端静态文件
        location /obs/ {
            alias  D:/server/nginx/html/obs/;
            index  index.html;
            try_files $uri $uri/ /obs/index.html;
        }

        # ② 网关
        location /gate/ {
            proxy_pass http://127.0.0.1:30901/gate/;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_connect_timeout 30s;
            proxy_read_timeout 300s;
            proxy_send_timeout 300s;
        }

        # ③ BSPPLUS
        location /ucenter/ {
            proxy_pass http://127.0.0.1:9099/;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_read_timeout 300s;
        }

        # ④ 行为分析占位页
        location /posthog/ {
            alias  D:/server/nginx/html/posthog/;
            index  index.html;
            try_files $uri $uri/ /posthog/index.html;
        }

        # ⑤ 工单系统：模拟「未找到工单」
        location = /dms/local/dsm-plugin-oms/api/order/getInfo {
            default_type 'application/json; charset=utf-8';
            add_header Cache-Control 'no-store';
            return 200 '{"state":0,"message":"TkOrder not found: DMS not connected"}';
        }

        # ⑥ 工单占位页
        location ^~ /dms/ {
            alias  D:/server/nginx/html/dms/;
            index  index.html;
            try_files $uri $uri/ /dms/index.html;
        }

        # ⑦ 前端配置文件禁缓存
        location ~ ^/obs/config\.[a-z0-9]+\.js$ {
            root   D:/server/nginx/html;
            add_header Cache-Control "no-cache, no-store, must-revalidate";
            add_header Pragma "no-cache";
            expires -1;
        }

        # ⑧ 根路径
        location = / { return 302 /obs/; }

        location / {
            root   D:/server/nginx/html;
            index  index.html;
        }
    }
}
```

#### 各 location 解释

| # | location | 作用 | 关键点 |
|---|---|---|---|
| ① | `/obs/` | 前端静态文件 | `alias` 而不是 `root`；`try_files` 兜底到 `index.html`（Vue history 路由需要） |
| ② | `/gate/` | 转发到网关 30901 | **`proxy_pass` 带 `/gate/` 路径**，网关侧再做 StripPrefix |
| ③ | `/ucenter/` | 转发到 BSPPLUS 9099 | 登录、菜单、SSO |
| ④ | `/posthog/` | 行为分析占位页 | PostHog 未部署 |
| ⑤ | `= /dms/…/getInfo` | **精确匹配**，直接返回 JSON | `=` 优先级最高；返回 `TkOrder not found` 让前端走友好分支 |
| ⑥ | `^~ /dms/` | 工单占位页 | `^~` 表示前缀匹配后不再检查正则 |
| ⑦ | `~ ^/obs/config\.…js$` | 配置文件禁缓存 | **正则匹配**，比前缀匹配优先级高（除 `^~` 和 `=`） |
| ⑧ | `= /` | 根路径重定向到 `/obs/` | — |

#### `location` 匹配优先级（Nginx 规则）

```
1. = /exact          精确匹配，最高优先级
2. ^~ /prefix        前缀匹配，命中后不再检查正则
3. ~  regex          正则匹配（按配置文件中的顺序，第一个命中的生效）
4. /prefix           普通前缀匹配，选最长匹配
```

#### 曾经遇到的问题

第一次插入 `/posthog/` 时**放错了大括号层级**（放到了 `server{}` 外面），
导致 `nginx -t` 报错、`nginx -s reload` 静默失败、页面一直 404。

**做法**：每次改完必须 `nginx -t` 验证，再 `-s reload`。

#### 2.5.2 `signozService-Cg3RwBMu.js` — SQL 修正

**改前**

```sql

```


**完整 SQL（改后）**

```sql
SELECT
    attributes_string['http.route'] AS `接口地址`,
    toFloat64(count()) AS `调用总次数`,
    toFloat64(countIf(toFloat64OrNull(response_status_code) >= 400)) AS `错误次数`,
    if(
        toFloat64(count()) > 0,
        (toFloat64(countIf(toFloat64OrNull(response_status_code) >= 400)) / toFloat64(count()) * 100),
        0
    ) AS `错误率(%)`,
    if(
        toFloat64(count()) > 0,
        if(
            (toFloat64(countIf(toFloat64OrNull(response_status_code) >= 400)) / toFloat64(count()) * 100) > 10,
            '异常', '正常'
        ),
        '无流量'
    ) AS `接口状态`
FROM signoz_traces.distributed_signoz_index_v3
WHERE timestamp BETWEEN {{.start_datetime}} AND {{.end_datetime}}
  AND attributes_string['http.scheme'] = 'http'
  AND attributes_string['http.target'] NOT LIKE '%/static/%'
  AND attributes_string['http.target'] NOT LIKE '%.css'
  AND attributes_string['http.target'] NOT LIKE '%.js'
  AND attributes_string['http.target'] NOT LIKE '%.png'
  AND attributes_string['http.target'] NOT LIKE '%.ico'
  AND attributes_string['http.route'] IN $http.route
GROUP BY `接口地址`
ORDER BY `调用总次数` DESC
```

**思路**

`http.target` = 完整请求路径（含 query string）；`http.route` = 路由模板（不含参数）。
前端传的是路由模板（`/xxx/yyy`），必须用 `http.route` 匹配才命中。

**这个 SQL 是通过 `POST /obs/business/signoz/proxy/api/v5/query_range` 转发的，

白名单**只放**登录/工具/SSO 这类必需免登录的路径，不放业务接口。

**注意**：`anon-white-list` 在本环境**不生效**（因为 `api-auth-check-enable: false` 关掉了对应过滤器），不要再往那里加。

## 写在最后

这 20 个问题里，只有 3 个是"配置写错了一个参数"。剩下的要么是**信息藏在二进制里**（jar 里的硬编码日期），要么是**跨越了多个组件**（网关拦了、前端 SQL 不对、服务器时钟还偏），要么是**报错信息完全误导**（应用启动失败但日志只说 `not initialize`）。

几点体会：

**1. 报错信息不可信的时候，去看底层。**

"启动即退出"看起来像配置问题、像网络问题、像授权问题，实际是 jar 里一个硬编码的日期字符串。这种信息，配置文件里永远找不到，只能反编译 class 看常量池。

**2. 现象和根因之间可能隔着好几层。**

"调用次数是 0"这一个现象，背后是三个独立的问题：SQL 匹配字段不对、网关的安全策略拦了查询请求、服务器时钟偏移把时间窗切掉了。修完前两个数字能出来了，但只出来一部分——第三个问题才让数字完全对上。

**3. 时间基准是所有监控的地基。**

可观测平台的所有查询都是"某段时间内的数据"。如果服务器时钟偏了 29 分钟，那所有"最近 N 分钟"的视图都在看历史数据，所有告警都会延迟。这个问题很难从界面上看出来，因为界面上的数字"看起来是正常的"，只是永远不更新。

**4. 文档里不会写的，才是真正花时间的地方。**

公司部署手册写的都是"配置这一项、启动服务、访问地址"。真实环境里的问题，是 License 过期、jar 版本不一致、bat 文件编码、双网卡地址填反这一类。这些只能靠现场踩。

如果这篇能让你少踩两个坑，那就值了。

## 附录 B 经验总结

### B.1 Windows 脚本类

| 问题 | 现象 | 正确做法 |
|---|---|---|
| `.bat` 用 LF 换行 | `'xxx' 不是内部或外部命令`、中文碎片被执行 | **必须 CRLF** |
| `.bat` 含中文 | cmd 解析乱码 | **纯 ASCII**，注释也用英文 |
| 管道接驻留进程 | 命令行永久挂住 | `Start-Process -WindowStyle Hidden`，不接管输出 |
| `docker exec` 用通配符 | `cannot access '/path/*'` | 写完整路径，或 `bash -c 'cmd *'` |

### B.2 前端补丁类

| 问题 | 正确做法 |
|---|---|
| 改了 `config.*.js` 不生效 | 换 `?id=` 版本号 + Nginx 对 config 禁缓存 |
| 报错被 `try/catch` 吞掉 | 我排查时先看 Console 报错，不要只看界面 |

### B.3 排查方法类

| 场景 | 方法 |
|---|---|
| 不知道某接口/某功能怎么实现的 | **反编译 jar**（`javap -p -c`），优先采用 |
| 不知道前端调的什么接口 | F12 → Network，看 URL + Payload + Response |
| 不知道请求被谁拒绝 | **看响应字段名**：`message` = 业务服务，`msg` = 网关 |
| 不知道数据为什么查不到 | **直连底层数据源验证**（ClickHouse / MySQL），再逐层往上看 |
| 大文件 / 大目录占用 | 按目录逐层统计（一级目录 → 子目录 → 单个文件） |
| 服务重启后起不来 | **先看 jar 里有没有硬编码的日期/授权检查**（`javap -p -constants`） |
| 数据「看起来没有采集」 | **先核对各服务器时钟**：`date -u` 逐台对比；时钟偏差会使 `BETWEEN now()-N AND now()` 的时间窗整体偏移 |

### B.4 判断是否为本次改动引入的问题

| 现象 | 判断依据 |
|---|---|
| 重启后起不来，日志有 `DateUtils.compareDate` | **不是配置问题**，是 jar 里硬编码到期日 |
| 换配置后还是不生效 | **先确认文件真的被加载了**（浏览器缓存 / 服务是否重启） |
| 功能一直返回空 | **先直连数据源验证数据存在**，再排除中间层 |
